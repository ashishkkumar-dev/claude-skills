Postgres internals: from a request to RAM

A request names a database and a table. Postgres changes these names into numbers, the numbers into a file path, and the file path plus a page number into a place in RAM.

The whole path in one picture

One query, UPDATE accounts SET balance = 500 WHERE id = 7, from the client to ClickHouse. Read the rows from top to bottom, and follow the arrows. Click a box to open its step.

The 12 steps in words

  1. Connect: pg_hba.conf, then the password in pg_authid, then the database OID in pg_database. This gives the folder base/16384.
  2. At the first query on a table: search_path → pg_namespace gives the schema OID (public = 2200). pg_class, with the table name and the schema OID, gives the table OID 16390 and file 24576. pg_attribute gives the columns, pg_index the indexes. All cached.
  3. Index or Seq Scan depends on the WHERE column and the row estimate.
  4. B-tree search in accounts_pkey (file 24580): metapage → top page → leaf page, one page per level. The leaf entry for 7 gives (42,3): table page 42, item 3 (line pointer 3).
  5. Page 42: Postgres looks in shared_buffers first, else reads it from the file (often from the OS cache).
  6. In RAM: pin count +1 and an exclusive content lock in the header of the page slot. Line pointer 3 gives the byte position of the row. Visible: t_xmin committed (in pg_xact) and t_xmax = 0. Write the new version: HOT = same page, no index change; normal = a new entry in every index.
  7. Add the WAL record to the WAL buffer, set pd_lsn, and mark the page dirty.
  8. COMMIT: write + fsync of the WAL file, then the commit status bits, then UPDATE 1 to the client.
  9. Later: page 42 goes to disk through the background writer, eviction or the checkpointer, always after its WAL.
  10. The WAL sender reads the WAL file, decodes it, waits for COMMIT, and sends B, R, U, C over the Postgres protocol on TCP.
  11. The client stores the change, then sends 'r'. The slot moves, and old WAL files can go.
  12. ClickHouse gets an INSERT, and a merge later keeps the newest row.

1The levels: server, database, schema, table

One server holds databases. A database holds schemas. A schema holds tables. Each object has a number.

The names can repeat. There are three different tables with the name accounts: shop.public.accounts, shop.sales.accounts and billing.public.accounts. Their numbers are different.

New terms

Database
A separate set of tables inside one server. A connection opens one database only. Example: shop.
Schema
A named group of tables inside one database. It is not a folder on disk. Example: public. The full name of a table is schema.table, for example public.accounts.
OID (object identifier)
A number that Postgres gives to each object: each database, schema and table. Example: the table public.accounts has OID 16390.

2The folders on disk

All data of a server is in one folder. Each database has its own subfolder. Some folders are shared by all databases.

The folder tree is beside this section (above it on a narrow screen). It stays visible, and it highlights the files that each section and each step uses.

  • Shared folders (orange): global/ with the list of databases and the list of roles, and pg_wal/, pg_xact/ and the other folders for all databases.
  • Database folders (blue): base/16384/ for shop and base/16385/ for billing. All schemas of a database are in its one folder.
  • Catalog tables (violet): 1262, 1260, 2615, 1259, 1249, 2610. Section 4 explains them.

File names in a database folder are numbers, not names. The numbers in the tree are examples.

New terms

Data directory ($PGDATA)
The one folder that holds all data of a server. Find it with SHOW data_directory;
Catalog
The tables in which Postgres stores the description of all objects: databases, schemas, tables, columns and indexes. They are normal tables with files, in the schema pg_catalog. Example: the list of tables is the file base/16384/1259.
File number (relfilenode)
The name of the file that holds a table or an index. It is different from the OID, because Postgres gives a table a new file after TRUNCATE or VACUUM FULL. Example: public.accounts has OID 16390 and file number 24576.

3The files of one table

One table has up to 3 files with the same number, and related objects with their own numbers. All of them are in the folder of the database.

New terms: the files of the table

Page
A block of 8 KB in a file. Postgres always reads and writes a full page. One page holds many rows. Example: page 42 of the file 24576 starts at byte 42 × 8,192 = 344,064.
Free space map
A small file next to the rows file. It records the free space of each page, so that a new row finds a page with space. Example: 24576_fsm.
Visibility map
A small file with 2 bits for each page. The bits say if all rows on the page are visible to all transactions, and if they are frozen. Example: 24576_vm.

New terms: the related objects

Index
A separate, sorted structure with its own file. It stores a column value and the address of the row. Example: accounts_pkey stores "id 7 is at page 42, item 3".
TOAST table
A separate table for large values. If a row is larger than approximately 2 KB, Postgres moves its large values there. Example: pg_toast.pg_toast_16390, file 24579.

4How the catalog numbers link together

Two numbers in the row of a table do all the work. The OID links the table to the other catalog tables. The file number gives the name of the data file.

A shared catalog table in global/. One row for each database. Example: datname shop, oid 16384.

One row for each column of each table. The column attrelid holds the table OID. Example: attrelid 16390, attname balance.

One row for each index. The column indrelid holds the table OID, and indkey gives the indexed columns. Example: indrelid 16390, indkey 1 (the column id).

A small file in each database folder. It gives the file numbers of the core catalog tables. Thus Postgres can read pg_class before it knows anything else. Example: pg_class is file 1259.

5The flow: from a request to RAM

Each step gives one number, and the next step needs that number. Select a step in the diagram to see what Postgres reads and why.

The example query for all steps

-- user app opens a connection to the database shop, then runs:
UPDATE accounts SET balance = 500 WHERE id = 7;

Postgres gets only names: the database shop, the table accounts and the column id. It must find the page that holds the row with id = 7.

How the index works

The index and the table are two different files. Each file numbers its own pages from 0, so "page 2" alone is not a full address.

  • There is no other table. The rows of accounts are in file 2. The index accounts_pkey is a separate file that holds only keys and row addresses.
  • A leaf entry always points into the table file. 7 → (2,3) means page 2 of accounts, never page 2 of the index.
  • The buffer tag contains the file number, so the two "page 2"s never mix in RAM.

The index is a tree. Each node of the tree is one page of the index file. A parent page holds the page numbers of its children.

A tree is a graph with 3 rules: each node can have many children; each node except the top node has exactly one parent; there are no loops, and all leaf pages are at the same depth.

A search for id = 7 follows one path: the top page sends it to the middle page "1 to 100,558", that page sends it to the leaf page "1 to 367", and the leaf page gives (2,3). That is 3 index pages for 1 million rows. Step 8 shows the calculation. The counts were measured on a test table of 1 million rows.

New terms

Tree of pages (B-tree)
The structure of a Postgres index. Each node is one 8 KB page with many sorted keys. Upper pages point to lower pages, and leaf pages point to rows. Example: accounts_pkey. A BST (binary search tree) has only 1 key in each node, so it needs many more reads.

An index page is 8 KB and has the same layout as a table page. It also has an area at the end with the links to its neighbour pages.

  • The same format as a table page: the 24-byte header (with pd_lsn), the line pointers and the free space.
  • The entries: a leaf page holds key + row address. An upper page holds key + page number. For an int4 key, one entry is approximately 16 bytes.
  • The end area: the previous page, the next page and the level. You can see them with bt_page_stats (columns btpo_prev, btpo_next, btpo_level).

New terms

The end area of an index page (special space)
The last bytes of each index page. They hold the previous page, the next page and the level. Example: btpo_prev = 0, btpo_next = 4, btpo_level = 0.
Sibling link
The link from a page to the previous and the next page at the same level, in key order. Example: leaf page 1 links to leaf page 4.

The metapage (page 0) records which page is the top page. When the top page splits, Postgres creates a new top page above it and writes its number into the metapage.

  1. New index. The file has page 0 (the metapage) and page 1. Page 1 is a leaf page and also the top page, so the metapage says "top = 1".
  2. First split. Page 1 is full. Postgres moves the upper half of its entries to a new page 2. It creates page 3 as the new top page, with 2 entries: "from 1 → page 1" and "from 401 → page 2". The metapage changes to "top = 3".
  3. More leaves. Each later leaf split adds a leaf page (4, 5, ...) and one entry in the top page. The top page keeps its number.
  4. The top page splits. It splits into page 3 and a new page 8. Postgres creates page 9 above them as the new top page, and the metapage changes to "top = 9". The tree has one more level.

The tree grows at the top, not at the bottom. Thus all leaf pages always stay at the same depth.

New terms

Page split
When a page is full, Postgres moves the upper half of its entries to another page, and adds an entry for that page in the parent page. Example: page 1 (keys 1 to 800) becomes page 1 (1 to 400) and page 2 (401 to 800).

6When each stage runs

Steps 1 to 3 run once for each connection. Steps 4 to 6 run at the first query on a table, then the connection uses its catalog cache (step 6). Steps 7 and 8 run for each query. Steps 9 and 10 run for each page.

Example: you connect to shop and run the same UPDATE on accounts three times. A blue dot means that Postgres reads the catalog.

  1. 10:00:00Connect to shop as user appSteps 1 to 3: the access rules, the list of roles, the list of databases.
  2. 10:00:05First UPDATE on accountsSteps 4 to 6: the lists of schemas, tables, columns and indexes. The results go into the catalog cache.
  3. 10:00:09Second UPDATE on accountsNo catalog read. The catalog cache has the data. Steps 7 to 10 only.
  4. 10:01:00Another connection runs ALTER TABLE accounts ADD COLUMN note textPostgres tells all connections that their cached data for accounts is old.
  5. 10:01:05Third UPDATE on accountsSteps 5 and 6 again, because the cached data was removed.
  6. 10:05:00A new connection to shopIts catalog cache is empty, so it runs all steps again. The catalog pages are usually still in RAM, so this is fast.

8Edge cases

The special cases from this part, for revision. Each card links to the step that explains it.

If: A schema in search_path does not exist

Postgres skips it and tries the next schema. Example: app is not found, so accounts is found in public.

If: Two databases have a table named accounts

Each database has its own catalog files in its own folder. Thus each accounts has its own OID and its own file.

If: The file number differs from the OID

TRUNCATE and VACUUM FULL write a new file. The file number changes, but the OID stays the same.

If: The WHERE column has no index

Only a Seq Scan is possible. Postgres reads all pages of the table and checks each row.

If: An index exists, but many rows match

A Seq Scan or a bitmap scan can be cheaper. The planner decides with the column statistics.

If: The table is bigger than shared_buffers

Postgres loads one page at a time and replaces rarely used pages. A large Seq Scan uses only 256 KB of shared_buffers.

If: A large UPDATE fills RAM with dirty pages

The query writes a dirty page to the OS itself (WAL first), then reuses the slot. It never waits for the checkpointer.

If: The OS has too many dirty pages

The OS page cache is RAM. When dirty pages reach 20% of RAM, write() waits for the disk. This is the real limit: disk speed.

If: The table has millions of rows

The index reads one page for each level, then one table page. 1 million rows: 4 reads. 27 million rows: 5 reads.

If: Many rows have the same key

Postgres reads the next leaf pages through the sibling links, and one table page for each matching row.

If: An insert fills an index page

The page splits into two. If the top page splits, the tree gets a new level at the top.

If: The page is already in RAM

Postgres finds its buffer tag in RAM and reads no file. It always checks RAM first.

If: The page left shared_buffers, but the OS still has it

Postgres calls read() on the table file. The OS gives the page from its page cache, with no disk read.

If: The page number is above 131,071

The page is in the next 1 GB part of the file. Example: page 200,000 is in 24576.1.

      1What is in RAM

      Part 1 ends with page 42 of accounts in RAM. This part shows what Postgres changes in RAM, and what goes to disk at COMMIT.

      RAM has two kinds of memory. All processes of the server use the shared memory. Each connection also has its own private memory.

      New terms

      Shared memory
      RAM that all Postgres processes of one server can read and change. Example: shared_buffers is in shared memory, so every connection sees the same copy of page 42.
      WAL buffer
      An area in shared memory for new WAL records. Postgres writes it to the files in pg_wal at COMMIT, or earlier. Example: the record for our UPDATE stays here until COMMIT (steps 6 and 8).
      Commit status (pg_xact)
      2 bits for each transaction ID: in progress, committed or aborted. Postgres keeps recent pages of pg_xact in RAM. Example: transaction 1001 changes from "in progress" to "committed" in step 9.

      2Why Postgres needs the WAL and the WAL buffer

      After COMMIT, the change must survive a power cut. Postgres can make it safe in two ways. The WAL is the faster way.

      Why the WAL is faster

      • A WAL record holds only the change, not the whole page. Example: 72 bytes, not 8,192.
      • Postgres adds records at the end of one file. The disk does not jump between places.
      • A page that changes 100 times goes to disk once, later. Without the WAL, it would go to disk 100 times.

      Why records go to the WAL buffer first

      • A write to a file is a call to the OS, and each call costs time. The buffer collects many records, and one call writes all of them.
      • Many connections add records at the same time. The buffer puts them in one sequence, in LSN order.
      • If many transactions commit at the same time, one fsync writes the records of all of them (group commit, step 8 of the flow in section 3).

      How the WAL repairs the data after a crash

      Postgres reads the WAL from the start point of the last checkpoint. For each record, it compares the LSN of the record with pd_lsn of the page. If the page is older, Postgres does the change again. If not, it skips the record.

      New terms

      Write to many places (random write)
      Writes that go to different places in the files, so the disk must move between them. Example: page 42 and page 7,310 of accounts at COMMIT.
      Write at the end of a file (sequential write)
      Each write starts where the last write ended. Disks do this fastest. Example: the WAL file.
      Repair after a crash (crash recovery)
      At start, Postgres reads the WAL from the last checkpoint and does again each change that is not yet in the page. Example: page 42 has pd_lsn 0/2FFF0A0, so the record at 0/3000148 is done again.

      4Edge cases

      The special cases from this part, for revision. Each card links to the section or step that explains it.

      Question: Why the WAL at all?

      Without it, COMMIT must write each changed 8 KB page in its place. The WAL writes one small record at the end of one file.

      Question: Why the WAL buffer?

      It collects records in RAM, so that one OS call and one fsync write the records of many transactions.

      If: The server stops before COMMIT

      The changes are only in RAM, so they are lost. This is correct, because the transaction did not commit.

      If: The server stops after COMMIT, before page 42 is on disk

      The WAL is on disk. At start, Postgres does the change again from the WAL record.

      If: The new version does not fit in page 42

      Postgres gets another page from the free space map. Each index gets a new entry.

      If: The UPDATE changes an indexed column

      No HOT update is possible. Each index gets a new entry, also on the same page.

      If: Another transaction updates id 7 at the same time

      It sees t_xmax = 1001, which is still running. It waits until 1001 ends.

      If: The first change of page 42 after a checkpoint

      The WAL record also holds a copy of the whole page, about 8 KB.

      If: A large UPDATE wrote page AB to the OS, and a new query needs it

      The new query looks in shared_buffers first. It does not find page AB, so it calls read() on the table file. The OS gives the page from its page cache in RAM, with no disk read. That copy is the newest version, also before it is on disk.

      If: RAM is full of dirty pages

      The query writes a dirty page to the OS itself, and does not wait for the checkpointer.

        1The big picture: from the WAL to ClickHouse

        Part 2 ends with the COMMIT of transaction 1001 in the WAL. This part follows that change to a ClickHouse table, through a CDC client. Part 4 shows one real client: GitLab's Siphon.

        • A CDC client is a program that reads the replication stream of Postgres and writes each change to another system.
        • Examples: Siphon (GitLab; part 4), PeerDB (ClickHouse Cloud uses it) and Debezium (it writes to Kafka).
        • Some clients first write to a durable queue, and a separate writer reads the queue. Other clients write directly to ClickHouse.
        • A replication slot (section 2) remembers how far the client has read the WAL. Thus the client can stop and continue without a gap.

        New terms

        Copy each change to another system (CDC, change data capture)
        A program reads each INSERT, UPDATE and DELETE of a database and sends it to another system. Example: balance 300 → 500 of id 7 also arrives in ClickHouse.
        Logical replication
        Postgres sends row changes (table, columns, values), not raw WAL bytes. Any program can read them. Example: "UPDATE public.accounts: id 7, balance 500". Physical replication sends the WAL bytes to a copy of the same server.
        Durable queue
        A message system that stores messages on disk, in order, until a reader confirms them. Example: NATS JetStream or Kafka. The event "accounts, id 7, balance 500" waits there until the writer takes it.

        What replica identity changes

        For an INSERT, the new row has all values, so the client knows everything. For a DELETE, no new row exists. The client must get some old values, or it cannot find the row to delete.

        Example query: DELETE FROM accounts WHERE id = 7; The row had id 7, balance 500, city 'Pune'.

        SettingThe D message holdsExtra WALUse it when

        For an UPDATE with DEFAULT: Postgres sends the old key only if the key changes. Our UPDATE changes balance, not id, so the U message has only N (the new row). Step 4 shows it.

        What a replication slot is

        A slot is a named bookmark in the WAL. Each slot belongs to one client.

        • A client creates its slot once, with a name. Example: cdc_slot.
        • Each time the client connects, it names its slot: START_REPLICATION SLOT cdc_slot LOGICAL 0/3000100. Postgres does not give a free slot to a client. Slots are not a shared pool.
        • Only one connection can use a slot at a time. A second client that names the same slot gets an error.
        • The slot stays when its client is offline. It still counts toward max_replication_slots, and it still keeps WAL. Only pg_drop_replication_slot() removes it.

        Where the slot keeps WAL: files on disk, not the WAL buffer

        • The WAL buffer (4 MB, in RAM, part 2) only holds new records until they are written. The slot has no effect on it.
        • On disk, the WAL is one long sequence of bytes, cut into files of exactly 16 MB. Postgres always writes at the end of the newest file. When that file is full, Postgres starts a new file.
        • The slot position points into one old file. Postgres keeps that file and all newer files. No file grows. The number of files grows.

        If the client never comes back: the files pile up until the disk is full, and then Postgres stops. Two settings prevent this. max_slot_wal_keep_size stops a slot that holds too much WAL. idle_replication_slot_timeout (Postgres 18) stops a slot that has had no client for too long. A stopped slot shows wal_status = lost, and its client must copy the tables again. Section 4 has these cases.

        New terms

        Publication
        A named list of tables in a database. Postgres sends only the changes of these tables. Example: cdc_pub contains accounts.
        Replication slot
        A bookmark in the WAL for one client. It stores how far the client has read, and Postgres keeps all WAL that the client still needs. Example: cdc_slot, with the confirmed position 0/3000100.
        Replica identity
        The setting of a table that selects which values of the old row Postgres writes into the WAL and sends for an UPDATE or a DELETE. Example: with DEFAULT, a DELETE of id 7 sends K: id = 7.

        Start state, from part 2: the WAL holds the HOT_UPDATE record (0/3000148) and the COMMIT record (0/3000190). The slot cdc_slot has the confirmed position 0/3000100. ClickHouse has one row for id 7, with balance 300.

        4Edge cases

        The special cases of this part, for revision. Each card links to the step that explains it.

        If: The CDC client stops

        The slot keeps all WAL after its confirmed position, so pg_wal grows by one 16 MB file for each 16 MB of new WAL.

        If: The slot holds too much WAL

        With max_slot_wal_keep_size, or idle_replication_slot_timeout (Postgres 18), Postgres stops the slot. The client then missed changes and must copy the tables again.

        If: The durable queue is down

        The client cannot store the change, so it does not confirm it. The slot keeps the WAL. Part 4 shows how Siphon handles this case.

        If: The client restarts

        It continues from confirmed_flush_lsn. Some changes arrive twice, and ClickHouse keeps one copy.

        If: The transaction ends with ROLLBACK

        The reorder buffer deletes its changes, also its spill files. The client gets nothing.

        If: One transaction changes more than 64 MB

        The WAL sender writes it to spill files in pg_replslot and reads them back at COMMIT. With streaming on, it sends the changes before COMMIT.

        If: The table has no primary key

        With REPLICA IDENTITY DEFAULT, an UPDATE or DELETE on a published table fails with an error. Add a key, or use USING INDEX or FULL.

        If: The UPDATE changes the primary key

        The U message also holds K, the old key, so the client can find the old row.

        If: A large TOAST value did not change

        pgoutput sends 'u' (unchanged) for it. The client must keep the old value.

        If: Someone adds a column

        Postgres sends a new R message before the next change of the table. The decoder uses the catalog at the LSN of each record.

        If: The table had rows before the slot

        The slot gives only new changes. The client copies the existing rows from a snapshot that matches the slot position.

        If: A ClickHouse query returns two versions of id 7

        The merge did not run yet. Use argMax over _version, or FINAL.

        If: A row is deleted in Postgres

        ClickHouse gets a new row with _is_deleted = 1. Queries filter it out, and the merge removes it.

          4Behavior that is not obvious

          These facts come from the code. Each one connects to a topic of parts 1 to 3.

          Streaming is off

          The plugin arguments set streaming 'false' (replication_manager.go:785). Thus a large transaction spills to files in pg_replslot on the Postgres server, and arrives at COMMIT as one block.

          Protocol version 2

          Siphon asks for proto_version '2' (line 782). PeerDB asks for version 1. Version 2 also allows streaming, but Siphon does not use it.

          No exported snapshot

          The slot is created with SNAPSHOT 'nothing' (create_replication_slot.go:18 and 31). Siphon copies existing rows later in its own REPEATABLE READ transaction, and routes new changes to a temporary stream meanwhile.

          The version is the write time

          The consumer sets _siphon_replicated_at to time.Now().UTC() of the batch (clickhouse_consumer.go:450). The design document says that it comes from the LSN (docs line 104). Ask the maintainers which one is correct.

          A failed flush stops the slot

          If a publish to NATS fails, the buffer is already empty. Siphon then sets an error flag, so that no later status update can move the slot past the lost events (replication_event_manager.go:228 to 236).

          Keepalives keep their order

          A 'k' frame goes into the same channel as the data (replication_manager.go:840 to 847). Thus Siphon confirms a keepalive position only after all earlier data.

          Pause without disconnect

          During a snapshot merge, Siphon stops reading but keeps the connection. It sends status updates with the same position, so wal_sender_timeout does not end the session (docs line 33).

          Emergency mode

          If NATS is down, pkg/failover writes the events to object storage with names that sort by LSN. When NATS returns, it replays them in LSN order.
